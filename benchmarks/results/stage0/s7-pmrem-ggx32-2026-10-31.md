# S7 runtime PMREM sample reduction — 31 Oct 2026

## Result

A guarded runtime override of Three.js 0.186.1's private PMREM GGX sample
define reduced the initial environment build from 469.8 ms to 154.6–156.9 ms
on the available RTX 4060 laptop. Tokyo arrival fell from 882.8 ms to 583.1–
583.2 ms across two full-city visible replays. The official globe-travel, walk,
night-switch, and street-travel segments stayed below 184 ms in both candidate
runs, with nine resident cells in Tokyo and Edinburgh and no console, page, or
HTTP errors.

The candidate improves the initial PMREM and the separate Tokyo-arrival stall,
but leaves one arrival frame above 500 ms. It does not close S7: Chrome used the
NVIDIA RTX 4060 on an i7-13650HX, not the target i5-1035G1. Target-device
performance and ground/terrain review remain open.

## Method and comparison

The application temporarily wraps `renderer.render` while
`PMREMGenerator.fromEquirectangular` runs. It recognizes only Three r186's
`PMREMGGXConvolution` material, changes its `GGX_SAMPLES` define to 32, and
restores the original renderer method in `finally`. Other renders are untouched.
If that private material marker is absent or the renderer cannot be wrapped,
Three.js keeps its default. Diagnostics record the effective sample count.
Implementation: [env-map.js](../../../lib/engine/env-map.js).

All runs used visible Chrome 156, the same 35,415,953-byte recorded Tokyo and
Edinburgh 3×3 cell fixture (SHA-256
`7DC24D83D85EBB984B31DEDC75596454621A4F8499CF59FA6D25B7EEC13BF6CE`), and the
normal GPU program cache. The original baseline and two candidate rows below
are inferred to have auto-selected high quality: each used a fresh browser
context, the store defaults to auto, and `applyAutoQuality` selects high for
this RTX adapter. Those earlier runner reports did not capture the active tier.
The first candidate run included CPU sampling during Tokyo arrival; the second
ran without CPU sampling.

| Run | Effective samples | Initial PMREM | Tokyo arrival max / p95 | Globe / walk / night / street max | Cells settled | Errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline, stock Three.js | 256 | 469.8 ms | 882.8 / 166.2 ms | 183.3 / 17.0 / 17.0 / 33.8 ms | 9/9, 9/9 | 0 |
| Runtime hook, profiled | 32 | 156.9 ms | 583.1 / 166.7 ms | 183.3 / 17.1 / 17.2 / 33.3 ms | 9/9, 9/9 | 0 |
| Runtime hook, unprofiled repeat | 32 | 154.6 ms | 583.2 / 133.7 ms | 183.5 / 17.0 / 16.9 / 33.3 ms | 9/9, 9/9 | 0 |

The 32-sample result matches the earlier package-patched diagnostic (160.1 ms
PMREM, 566.7 ms Tokyo arrival) while keeping `node_modules` at its stock 256
setting. The production build and focused ESLint check passed with the runtime
hook as the only application change.

The profiled candidate's longest Tokyo-arrival Long Task lasted 591 ms. The
156.9 ms PMREM build completed before a 386.6 ms ordinary renderer program
event that added 16 programs (3 to 19). The CPU profile sampled 251.7 ms in
`getProgramInfoLog` on the regular render path, separate from PMREM. The sample
reduction therefore removes most of the environment-build cost but leaves
first-city-render shader linking as the dominant residual. Earlier PMREM shader
precompile and frame-budgeted warmup attempts are documented in the
[full 3×3 replay report](s7-full-city-3x3-profile-2026-10-31.md).

## Medium-quality configuration diagnostic

The RTX 4060 auto-selects high quality, while the target Intel UHD laptop
auto-selects medium. The tour runner now accepts `--quality=medium`, sets that
manual tier only in its isolated browser context, and records the engine's
actual `qualityTier`. This reproduces the target quality configuration but not
its GPU or CPU.

Three further full-city visible replays used medium quality and the 32-sample
PMREM override. Two normal-cache runs measured 148–149.9 ms PMREM and 450.0–
450.1 ms Tokyo arrival; their first renderer program events added 12 programs
in 267.4–272.2 ms. A run with Chrome's GPU program cache disabled measured
159.6 ms PMREM and 499.9 ms Tokyo arrival, with 12 programs added in 286.4 ms.
All four named S7 gate segments remained below 200 ms in each run, all 9/9
cells settled in both cities, and console, page, HTTP, and request-failure
counts were zero. The cold-cache result has only 0.1 ms of headroom at the
500 ms arrival threshold; it is not robust margin, and none of these runs is
target-device acceptance evidence.

comparison against the existing 256-sample captures found mean absolute channel
differences of 0.40/255 for Tokyo arrival, 0.92/255 for Tokyo night, and
0.95/255 for Edinburgh arrival; 0.32%, 0.25%, and 0.08% of channels respectively
differed by more than 10. These captures are a quick image check, not a matched
