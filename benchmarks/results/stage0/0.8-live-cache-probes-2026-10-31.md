# 0.8 local live-cache probes — 31 October 2026

Status: preliminary diagnostics only. These captures do not close the matched production-baseline gate.

## Setup and scope

All six captures used visible Chrome 156.0.8078.79 in browser-default WebGL mode at 1280×720, DPR 1, Medium quality, on a Lenovo 83DV with a 13th Gen Intel Core i7-13650HX (14 cores / 20 logical processors), NVIDIA GeForce RTX 4060 Laptop GPU, and Intel UHD Graphics. The selected renderer was ANGLE / NVIDIA RTX 4060 / D3D11; `integratedGpu` was false. Windows reported the High performance power scheme. The browser was visible and focused during the recorded windows, with no focus or visibility losses.

The app ran at `http://localhost:3456` on the Next.js development server. The production build had passed, but the local production server could not be launched under the command policy, so these are development-server measurements. Runs were about eight seconds each and had one repetition per scenario.

New York used the configured public city-cache read path. Cold means a fresh Playwright context; warm means the origin cell was loaded first and its IndexedDB entry verified before measuring a new page in the same context. All four New York scenarios stayed in the origin cell (`crossCell=false`) and reported no `/api/city` cell requests. These are origin-cell cache-path probes, not boundary runs. The browser's upstream server and CDN caches were not controlled by the cold/warm protocol.

Edinburgh used the local city API with the regional Britain and Ireland Overpass endpoint and no public R2 base. Its cold-walk and warm-drive runs crossed into a neighboring cell; both validated the transition with ten resident cells and no failed cell keys. The measured API delivered 12 city cells in the cold walk and 11 in the warm drive, all HTTP 200. No private R2 credentials or writes were used.

## Reading the results

The large frame-time tails are material: each run recorded nine or ten measurement-window frames above 100 ms. The Edinburgh warm-drive GPU p95 also reached 485.15 ms. These one-off tails need diagnosis and repeated capture before comparing performance or describing a stable baseline. The New York warm-drive frame p95 was 33.1 ms, but its p99 was 500.2 ms; the p95 alone does not represent the full stall behavior.

The capture metadata marks every run `sourceTreeDirty=true`. Five report source revision `4dc004516aab664242019f387f77102050806261`; the Edinburgh cold walk reports `121117ee275cfdb7914a74ea95431290e151a4d5`. They therefore are not a clean, same-revision matrix. No screenshot comparison, five-run repetition, target i5-1035G1 laptop run, or mobile thermal soak is included.

All six reports show zero console errors, page errors, asset failures, and HTTP error responses. Network telemetry nevertheless records two or three failed request events per run, with no HTTP status >=400; the captures do not identify these events well enough to classify them further. Keep this distinction when reviewing the results.

Prior invalid attempts are excluded: the Manhattan cold-walk Overpass path returned 502/aborted, and New York cross-cell cache probes encountered absent public-cache keys and API fallback failures. They are not valid baseline samples.

## Remaining 0.8 work

- Repeat cold/warm walking and driving boundary runs on the production origin with complete neighboring city data; use five repetitions per scenario and verify the actual renderer, request results, movement, and cell-streaming checks.
- Diagnose the repeated >100 ms tails and Edinburgh warm-drive GPU timer tail before interpreting frame-time differences.
- Control and record foreground state, OS load, power state, and browser cache setup across repetitions.
- Run the resource and thermal soak on real mobile hardware. Windows desktop thermal readings were unavailable.

These probes document cache and boundary paths while leaving the production, repeatability, and mobile acceptance gates open.
