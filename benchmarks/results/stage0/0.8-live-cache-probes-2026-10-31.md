## Setup and scope

The six local captures used visible Chrome 156.0.8078.79 in browser-default WebGL mode at 1280×720, DPR 1, Medium quality, on a Lenovo 83DV with a 13th Gen Intel Core i7-13650HX (14 cores / 20 logical processors), NVIDIA GeForce RTX 4060 Laptop GPU, and Intel UHD Graphics. The selected renderer was ANGLE / NVIDIA RTX 4060 / D3D11; `integratedGpu` was false. Windows reported the High performance power scheme. The browser was visible and focused during the recorded windows, with no focus or visibility losses.

The six local runs used `http://localhost:3456` on the Next.js development server. The production build had passed, but the local production server could not be launched under the command policy, so these are development-server measurements. Each is one run with an approximately eight-second measurement window.

New York used the configured public city-cache read path. Cold means a fresh Playwright context; warm means the origin cell was loaded first and its IndexedDB entry verified before measuring a new page in the same context. All four New York local scenarios stayed in the origin cell (`crossCell=false`) and reported no `/api/city` cell requests. These are origin-cell cache-path probes, not boundary runs. The browser's upstream server and CDN caches were not controlled by the cold/warm protocol.

Edinburgh used the local city API with the regional Britain and Ireland Overpass endpoint and no public R2 base. Its cold-walk and warm-drive runs crossed into a neighboring cell; both validated the transition with ten resident cells and no failed cell keys. The measured API delivered 12 city cells in the cold walk and 11 in the warm drive, all HTTP 200. No private R2 credentials or writes were used.

One additional cold-walk run used the production origin, `https://walk-the-world-delta.vercel.app`, at New York coordinates `40.758, -73.9855`. The service-worker cache revision served by production matched the revision generated for commit `58c8366`, confirming the deployed build. The run used the same RTX 4060 renderer and cold browser-context protocol; measurement validation passed with full frame coverage, zero city API requests, only HTTP 200 responses, and no console, page, or asset errors. Host telemetry covered 7 of 8 expected samples (88%). This is a single origin-cell sample, not a boundary or repetition matrix.

## Reading the results

The large tails persist on the production origin: its one New York cold walk recorded ten of 189 frame intervals above 100 ms, with p95 466.5 ms and p99 516.6 ms. The corrected production cold walk reproduces the same roughly 0.5 s gaps, so development-server overhead is not the sole cause.

Across the seven captures, renderer frame timestamps match the recorded frame intervals to within 0.8 ms median absolute difference. The high intervals therefore reflect actual gaps between rendered frames, not a percentile-summary artifact. No recorded Long Task overlaps those high intervals. The asynchronous GPU timer also reports repeated >100 ms samples that mostly line up with the frame gaps after its polling delay (one frame in five of the six local captures; same-index alignment in the production capture). This points toward a graphics-pipeline or driver stall, but the association is index-based: `gpuFrameTimesMs` stores scalar durations without source-frame timestamps, so the exact cause is not localized.

The Edinburgh warm-drive GPU p95 reached 485.15 ms. The production New York sample had GPU p95 473.12 ms, while the local New York walk and drive samples had GPU p95 around 18–30 ms despite similar frame-interval tails. Do not use the GPU p95 values alone to compare these samples until GPU results can be joined to their source frames.

The capture metadata marks all six local runs `sourceTreeDirty=true`. Five report source revision `4dc004516aab664242019f387f77102050806261`; the Edinburgh cold walk reports `121117ee275cfdb7914a74ea95431290e151a4d5`. The production capture used local harness source revision `58c8366b99729c397f330e58719bf1e82f47edba` with a clean tree; the deployed service-worker revision confirmed that production was serving the corresponding build. No screenshot comparison, five-run repetition, target i5-1035G1 laptop run, or mobile thermal soak is included.

All six local reports show zero console errors, page errors, asset failures, and HTTP error responses. Network telemetry nevertheless records two or three failed request events per run, with no HTTP status >=400; the captures do not identify these events well enough to classify them further. The valid production capture has zero failed requests and zero HTTP errors.

Prior invalid attempts are excluded: the Manhattan cold-walk Overpass path returned 502/aborted; New York local cross-cell probes encountered absent public-cache keys and API fallback failures; and an initial production run at the benchmark's default Rome coordinates received two 404s for missing neighboring cells. The Rome run was replaced by the corrected New York origin-cell capture. None is a valid baseline sample.

## Remaining 0.8 work

- Localize the recurring graphics-pipeline/driver stalls using a timestamped GPU trace or browser GPU profile; preserve the source-frame association for timer results.
- Repeat cold/warm walking and driving boundary runs on the production origin with complete neighboring city data; use five repetitions per scenario and verify the actual renderer, request results, movement, and cell-streaming checks.
- Control and record foreground state, OS load, power state, and browser cache setup across repetitions.
- Run the resource and thermal soak on real mobile hardware. Windows desktop thermal readings were unavailable.

These probes document cache and boundary paths, confirm that the frame-gap pattern also appears on production, and leave the production repeatability and mobile acceptance gates open.
