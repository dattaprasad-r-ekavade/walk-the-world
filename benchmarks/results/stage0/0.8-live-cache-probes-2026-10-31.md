New York used the configured public city-cache read path. The browser's upstream server and CDN caches were not controlled by the cold/warm protocol.

Its cold-walk and warm-drive runs crossed into a neighboring cell; both validated the transition with ten resident cells and no failed cell keys. The measured API delivered 12 city cells in the cold walk and 11 in the warm drive, all HTTP 200. No private R2 credentials or writes were used.

One additional cold-walk run used the production origin, `https://walk-the-world-delta.vercel.app`, at New York coordinates `40.758, -73.9855`. The service-worker cache revision served by production matched the revision generated for commit `58c8366`, confirming the deployed build. The run used the same RTX 4060 renderer and cold browser-context protocol; measurement validation passed with full frame coverage, zero city API requests, only HTTP 200 responses, and no console, page, or asset errors. Host telemetry covered 7 of 8 expected samples (88%). This is a single origin-cell sample, not a boundary or repetition matrix.

## Reading the results

The large tails persist on the production origin: its one New York cold walk recorded ten of 189 frame intervals above 100 ms, with p95 466.5 ms and p99 516.6 ms. The corrected production cold walk reproduces the same roughly 0.5 s gaps, so development-server overhead is not the sole cause.

Across the seven benchmark captures, renderer frame timestamps match the recorded frame intervals to within 0.8 ms median absolute difference. The high intervals therefore reflect actual gaps between rendered frames, not a percentile-summary artifact. The benchmark files’ Long Task lists do not overlap their sampled high intervals. A separate visible Chrome trace of the production page recorded 10 gaps between `FireAnimationFrame` events, each 486–600.5 ms; every gap overlapped a Chrome GPU-thread `DXGISwapChainImageBacking::Present` call lasting 485.3–528.3 ms. In one 600.5 ms app animation callback, `GLES2Implementation::CheckFramebufferStatus` and its command-buffer wait consumed 495.2 ms. This narrows the observed stutter to DXGI presentation plus a synchronous WebGL wait in one frame, but does not establish why those waits occur or whether the same pattern appears on the target laptop. The GPU timer in the benchmark still stores scalar durations without source-frame timestamps, so its cross-run association remains index-based.

The Edinburgh warm-drive GPU p95 reached 485.15 ms. The production New York sample had GPU p95 473.12 ms, while the local New York walk and drive samples had GPU p95 around 18–30 ms despite similar frame-interval tails. Do not use the GPU p95 values alone to compare these samples until GPU results can be joined to their source frames.

The capture metadata marks all six local runs `sourceTreeDirty=true`. Five report source revision `4dc004516aab664242019f387f77102050806261`; the Edinburgh cold walk reports `121117ee275cfdb7914a74ea95431290e151a4d5`. The production capture used local harness source revision `58c8366b99729c397f330e58719bf1e82f47edba` with a clean tree; the deployed service-worker revision confirmed that production was serving the corresponding build. No screenshot comparison, five-run repetition, target i5-1035G1 laptop run, or mobile thermal soak is included.

All six local reports show zero console errors, page errors, asset failures, and HTTP error responses. Network telemetry nevertheless records two or three failed request events per run, with no HTTP status >=400; the captures do not identify these events well enough to classify them further. The valid production capture has zero failed requests and zero HTTP errors.

Prior invalid attempts are excluded: the Manhattan cold-walk Overpass path returned 502/aborted; New York local cross-cell probes encountered absent public-cache keys and API fallback failures; and an initial production run at the benchmark's default Rome coordinates received two 404s for missing neighboring cells. The Rome run was replaced by the corrected New York origin-cell capture. None is a valid baseline sample.

## Remaining 0.8 work

- Localize the recurring graphics-pipeline/driver stalls using a timestamped GPU trace or browser GPU profile; preserve the source-frame association for timer results.
- Repeat cold/warm walking and driving boundary runs on the production origin with complete neighboring city data; use five repetitions per scenario and verify the actual renderer, request results, movement, and cell-streaming checks.
- Control and record foreground state, OS load, power state, and browser cache setup across repetitions.
- Run the resource and thermal soak on real mobile hardware. Windows desktop thermal readings were unavailable.

These probes document cache and boundary paths, confirm that the frame-gap pattern also appears on production, and leave the production repeatability and mobile acceptance gates open.

## Production boundary attempt — incomplete outer cache strip (31 October 2026)

A visible Chrome 156 run against the production origin used a fresh browser
context, New York coordinates `40.758, -73.9855`, Medium/manual quality,
`browser-default` rendering, and a 12 s cold walk. Source revision was
`9823eb7`; the host was the i7-13650HX / RTX 4060 laptop, not the target
i5-1035G1.

The run loaded in 8,867 ms and recorded a valid 12,009 ms measurement window
with 286 frame intervals. It moved 29.42 m and crossed from
`wtw_city6_40.758_-73.986` to the expected
`wtw_city6_40.758_-73.980` cell. However, after the crossing, the shifted
3×3 neighborhood requested an eastern strip that is not in the current public
cache. HEAD checks returned 404 for `wtw_city6_40.758_-73.975`,
`wtw_city6_40.752_-73.975`, and `wtw_city6_40.764_-73.975`. Two city API
requests returned 502 and the third remained incomplete; the stream reported
`settled=false`. The run also logged four external HTTP 404s and six console
errors overall, with no page errors. It therefore fails the boundary acceptance
gate despite crossing into the expected neighbor.

The diagnostic frame summary was p95 33.4 ms, p99 516.2 ms, and 14 of 286
intervals over 100 ms. Because the new cell neighborhood did not settle and
requests failed, do not treat these as a valid production baseline or compare
them with the earlier captures. The raw ignored result is
`0.8-new-york-production-cold-walk-boundary-2026-10-31.json`.

A one-cell eastward crossing from this origin needs three additional eastern
cache cells to settle the shifted 3×3 window. The current nine-cell New York
start neighborhood does not include that strip, and the Overpass fallback was
unavailable during this run. No R2 writes occurred. The local staging CLI now
has an explicit `--stage-new-cell` mode for absent cache keys and
`--allow-out-of-group-key` for one-off outside-group keys; the fetch path was not exercised because
the Overpass mirrors were failing.
